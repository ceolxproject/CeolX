## Description

Define the three core identity tables. These are the foundation every other table references. The design must enforce the Option A persona model: one account, one active persona at a time, no data deletion on switch — just `is_active` toggling.

## Key Design Decisions

- **No `spectator_profiles` table**: Spectators have no public profile. Their activity is tracked through `follows`, `saved_events`, and `notifications` which all FK to `users`.
- **`artist_profiles.user_id` UNIQUE** constraint enforces one artist profile per user account. Switching back to Artist persona reactivates the existing profile (`is_active: true`) rather than creating a new one.
- **`venue_profiles.subscription_status`** is a denormalized copy of `venue_subscriptions.status`. Updated by the Stripe webhook handler (M8-T2). Denormalized to avoid a JOIN on every venue visibility check.
- **`ON DELETE CASCADE`** on both profile FKs: deleting a user account removes their profiles. No orphaned profiles possible.

## Common Gotchas

- **Switching personas, not deleting profiles**: Application logic must flip `is_active`, never `DELETE` a profile row. Add a comment in the schema file as a reminder.
- **`hashed_password` nullable**: BetterAuth creates users via Google/Apple Sign-In with no password. Always check for null before any password comparison.
- **`venue_profiles.is_active` vs `subscription_status`**: `is_active` is the gate for visibility. `subscription_status` tracks the Stripe lifecycle. A venue can be `subscription_status: active` but `is_active: false` during the brief window between webhook receipt and profile activation.
