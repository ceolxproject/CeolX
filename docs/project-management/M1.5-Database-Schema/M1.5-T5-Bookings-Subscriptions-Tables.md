## Description

Define the two commercial tables. `bookings` models the bidirectional Artist ↔ Venue engagement flow. `venue_subscriptions` models the Stripe subscription lifecycle — this is the source of truth for billing, while `venue_profiles.subscription_status` is the denormalized cache.

## Key Design Decisions

- **`direction` enum on bookings**: Determines who initiated the booking. `venue_to_artist` = venue sent invitation; `artist_to_venue` = artist applied to a gig opportunity. Both use the same table — the direction disambiguates UI labels and notification copy.
- **`event_id` nullable on bookings**: A venue can send a general inquiry to an artist without attaching it to a specific event. `event_id = NULL` represents this case.
- **`venue_subscriptions.venue_id` UNIQUE**: One active subscription per venue at a time. If a venue cancels and resubscribes, the existing row is updated (not a new row inserted) — subscription history is in the Stripe dashboard, not in CeolX DB.
- **Denormalization**: `venue_subscriptions.status` → `venue_profiles.subscription_status`. The Stripe webhook handler (M8-T2) updates both atomically in a transaction. If the transaction fails, a retry from the webhook will reconcile.
- **No message/thread table in V1**: Booking communication happens through the booking status state machine + notifications. Full messaging is post-V1.

## Booking State Machine

```
pending
  ├── accepted   (other party accepts)
  │     └── cancelled  (either party, any time)
  └── rejected   (other party rejects)
        └── [terminal — cannot reopen]
```

Enforce at application layer (Hono route handler), not via DB constraints.

## Common Gotchas

- **Stripe IDs as varchar**: Stripe customer and subscription IDs are strings (`cus_xxx`, `sub_xxx`) — never store as integers. Length 255 is sufficient; Stripe IDs are currently ~18 chars with prefix.
- **`plan` as varchar not enum**: Lite/Pro tiers are not finalised with the client (Open Item #2 in CLAUDE.md). Using `varchar` avoids a painful enum migration when tiers are confirmed.
- **Booking uniqueness**: There is intentionally no unique constraint on `(artist_id, venue_id)` — multiple bookings between the same pair are valid (different events, different time periods).
