## Description

Define the event-related tables. The `events` table is the most query-intensive table in the system — it serves the map viewport query, the discovery feed, the moderation queue, and creator dashboards. Getting the indexes right here is critical for M3 map performance.

Note: `collections` must be defined **before** `events` because `events.collection_id` FKs to `collections.id`. Drizzle handles forward references, but it's cleaner to declare `collections` first in the file.

**Indexes on `events`**:

| Index Name               | Type   | Columns / Expression                          | Purpose                                   |
| ------------------------ | ------ | --------------------------------------------- | ----------------------------------------- |
| `events_spatial_idx`     | GIST   | `ll_to_earth(lat, lng)` WHERE status='active' | Fast bounding-box map queries             |
| `events_status_date_idx` | B-tree | `(status, date_start)`                        | Filter active upcoming events in feed/map |
| `events_created_by_idx`  | B-tree | `(created_by, status)`                        | Creator's "My Events" list                |

**Check constraints on `events`**:

- `date_end IS NULL OR date_end >= date_start`
- `lat BETWEEN 51 AND 55` (valid Irish latitude range)
- `lng BETWEEN -11 AND -5` (valid Irish longitude range)

| Column       | Type      | Constraints               | Notes             |

## Key Design Decisions

- **`numeric(10,7)` for lat/lng**: Float types lose precision at 6+ decimal places. `numeric` stores exact values — at 7 decimal places, precision is ~1.1 metres, sufficient for pin placement.
- **GIST index with `WHERE status = 'active'`**: Partial index — only active events are indexed, keeping the index small and fast. Draft/rejected/archived events never appear on the map.
- **`ll_to_earth`**: PostgreSQL built-in function (requires `earthdistance` + `cube` extensions — enabled by default on Neon and available in PostgreSQL 16). Enables correct spherical distance queries without PostGIS.
- **SET NULL on `venue_id`**: If a venue account is deleted, the event loses its venue FK but the event itself survives. `venue_address` (free-text) acts as the permanent display fallback.
- **`is_gig_opportunity`**: Boolean flag on the event row — no separate table needed for V1. API layer filters this out for Spectator-role requests.
- **`view_count` denormalization**: Avoids expensive COUNT queries on a separate analytics table for feed ranking in V1. Will be replaced by a proper analytics table in V2.

## Spatial Index — Setup Note

The `ll_to_earth` function requires the `earthdistance` and `cube` PostgreSQL extensions. Run once per database:

```sql
CREATE EXTENSION IF NOT EXISTS cube;
CREATE EXTENSION IF NOT EXISTS earthdistance;
```

On Neon, these extensions are pre-installed. For the local Docker container, add an init SQL file:

```
docker/init/01-extensions.sql → CREATE EXTENSION IF NOT EXISTS cube; CREATE EXTENSION IF NOT EXISTS earthdistance;
```

## Sample Bounding-Box Query

```sql
-- Map viewport query (SW: 53.0, -8.5 → NE: 54.0, -7.5)
SELECT id, title, lat, lng, category, date_start
FROM events
WHERE status = 'active'
  AND lat BETWEEN 53.0 AND 54.0
  AND lng BETWEEN -8.5 AND -7.5
  AND date_start >= NOW()
ORDER BY date_start ASC
LIMIT 50;
```

Run `EXPLAIN ANALYSE` on this query after migration to verify the GIST index is used.

## Common Gotchas

- **`collections` before `events`**: `events.collection_id` FKs to `collections`. Define `collections` first in the schema file to avoid Drizzle forward-reference issues.
- **Drizzle GIST syntax**: Use `.using("gist", sql`...`)` — the standard `.on()` builder does not support GIST. Reference the existing M1-T2 schema snippet for correct syntax.
- **Check constraints in Drizzle**: Use `sql` template literals inside the table callback: `.check("date_range", sql`${table.dateEnd} IS NULL OR ${table.dateEnd} >= ${table.dateStart}`)`.
- **Neon extension enablement**: Run the extension SQL once on each Neon branch (dev/staging/prod) via the Neon SQL editor — not via migration, as extensions are per-database not per-schema.
