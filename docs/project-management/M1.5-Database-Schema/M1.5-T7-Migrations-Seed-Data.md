## Description

Run the generated migrations against all three environments (local Docker, Neon staging, Neon prod) and verify all 14 tables are created correctly. Insert minimal seed data into local and staging for manual testing during M2 development.

This is the final step before any feature milestone begins.

## Affected Files

- `apps/server/drizzle/migrations/` — generated SQL files (committed to repo)

## Requirements

### 1. Generate Migration

```bash
cd apps/api
npm run db:generate
# Produces: drizzle/migrations/0001_initial_schema.sql
```

Review the generated SQL before applying:

- 7 `CREATE TYPE ... AS ENUM` statements
- 14 `CREATE TABLE` statements
- All `CREATE INDEX` and `CREATE UNIQUE INDEX` statements
- All `ALTER TABLE ... ADD CONSTRAINT CHECK` statements

### 2. Apply Migration — Local Docker

```bash
# Ensure Docker is running
docker compose up -d

# Apply migration
DATABASE_URL=postgresql://ceolx:ceolx_local@localhost:5432/ceolx_dev npm run db:migrate
```

Verify with `psql` or Drizzle Studio (`npm run db:studio`):

- `\dt` — lists all 14 tables
- `\d events` — confirms GIST index on `(ll_to_earth(lat, lng))`

### 3. Apply Migration — Neon Staging

```bash
DATABASE_URL=<neon-staging-url> npm run db:migrate
```

Verify via Neon console → staging branch → Tables view.

### 4. Apply Migration — Neon Production

```bash
DATABASE_URL=<neon-prod-url> npm run db:migrate
```

Production migration applied before any feature code reaches `main`. Schema is stable — no feature code depends on it yet.

## Common Gotchas

- **Migration file committed**: Generated SQL in `drizzle/migrations/` must be committed to the repo. Drizzle tracks applied migrations in a `__drizzle_migrations` table — the SQL files are the source of truth. Never edit them by hand after applying.
- **Extension pre-flight**: Before running the migration on a fresh Neon branch or Docker container, ensure `cube` and `earthdistance` extensions are enabled (see M1.5-T3). The migration itself does not run `CREATE EXTENSION` — this is a one-time manual step per database.
- **Neon prod migration timing**: Apply the prod migration before M2 code is merged to `main`. The schema should always be ahead of the application code — never behind.
- **`process.exit(0)` in seed**: Without an explicit exit, the Neon serverless driver keeps the connection pool open and the script hangs. Always call `process.exit(0)` at the end of the seed function.
