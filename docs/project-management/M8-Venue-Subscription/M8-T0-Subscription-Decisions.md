## 3 · Subscription states

| State       | Meaning                                             | Venue visible? |
| ----------- | --------------------------------------------------- | -------------- |
| `inactive`  | Signed up, never completed payment setup            | No             |
| `trialing`  | Card saved, inside the free period, not yet charged | **Yes**        |
| `active`    | Paying subscriber                                   | **Yes**        |
| `past_due`  | A charge failed; Stripe is still retrying (D-33)    | **Yes**        |
| `cancelled` | Subscription ended, paid period elapsed             | No             |

| `D-nn`   | Decision                                                                                                                                                                                                                                      |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D-10** | `SUBSCRIPTION_STATUSES` in `packages/shared/src/enums.ts:54` must gain **`trialing`**. Without it the trial has no state to occupy.                                                                                                           |
| **D-11** | Store Stripe's status; do **not** collapse `trialing` into `active`. A translation layer means our DB and the Stripe dashboard disagree during an incident.                                                                                   |
| **D-12** | Stripe spells it `canceled`, we spell it `cancelled`. One explicit mapping function, one place.                                                                                                                                               |
| **D-13** | The visibility predicate is `status IN ('trialing','active','past_due')` — one helper, used by every caller. Never inline the status list.                                                                                                    |
| **D-14** | One fact, one column. Today it lives in three: `venue_subscriptions.status`, `venue_profiles.subscriptionStatus`, `venue_profiles.isActive`. Collapse before writing the webhook. `venue_profiles.isActive` is redundant for venues and goes. |

> ⚠️ `isActive` means "subscription active" on `venue_profiles` (default `false`) but "persona not switched away" on `artist_profiles` (default `true`). Same name, opposite meaning, in tables that get joined. Removing it from venues also removes this footgun.

## 6 · Charges, failures and the grace period

| `D-nn`   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D-33** | **7-day grace period, owned by Stripe.** Profile stays visible while Stripe retries the charge; hidden once Stripe gives up. **Revised 18/08/2026:** originally implemented as our own arithmetic — `past_due_since + 7 days` compared against our clock — which duplicated Stripe's native retry schedule and could disagree with it, hiding a venue Stripe was still successfully chasing or keeping one visible after Stripe had stopped trying. ## 9 · What happens to content when a venue stops paying

"Stops paying" means any of: trial ended without payment, failed payment past the grace window, cancellation period elapsed, refund, or chargeback.

### 9.1 The governing principle

| `D-nn`   | Decision                                                                                                                                                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D-52** | **Every unpaid-venue surface must attribute the absence to the venue, and offer the viewer a way forward.** Sean's reasoning: it must read as the venue not having paid, never as CeolX failing to show the venue. A dead end inverts the intent. |
| **D-53** | Nothing is ever deleted. Every rule below is reversible the instant payment resumes.                                                                                                                                                              |

### 9.2 Per-surface matrix

### 9.3 The implementation trap in V-03 vs V-06

Because V-03 hides venue-created events while V-06 keeps artist-created ones, **"is this event hidden" depends on who created it**. Map and feed read from Typesense, whose event document (`creator_id`, `venue_name`, `venue_address`, `status` — see `packages/api/src/services/event-sync.ts`) carries neither the venue subscription state nor `venue_id`.

| `D-nn`   | Decision                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D-54** | **Post-filter after Typesense returns. Do not put venue subscription state into the index.** Indexing it drags in a fan-out job re-indexing every one of a venue's events on each subscription change, plus a consistency window where a venue that just paid is still invisible. Map caps at 50 pins and feed pages are small, so one `venue_id → status` lookup over the returned ids is cheap and always correct. |
| **D-55** | Ceiling to record in a `ponytail:` comment at the call site: if unpaid venues ever become a large share of results, over-fetching stops covering the shortfall and the flag moves into the index.                                                                                                                                                                                                                    |

### 9.4 · Decisions behind the matrix

| `D-nn`   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **D-56** | **Bookings survive an unpaid venue.** Accepted bookings are untouched — a real-world agreement between two people is not cancelled by a lapsed card. Pending invitations **stay actionable**: accepting an invitation that already exists completes a link rather than forming a new one, so it does not conflict with V-09's block on _new_ links, and blocking it would penalise the artist for the venue's billing problem. Sean: _"we must protect the gigs and artists at all cost."_ |
| **D-57** | **Past-due is graduated.** Inside the 7-day grace window (D-33): full use, banner only — the grace period exists to absorb an expired card, so freezing during it defeats the purpose. After the window expires: a **holding block over the live map**, with view of their own content, profile editing and fix-payment still reachable. Creating events and posts is blocked whenever unpaid, in both phases.                                                                             |
| **D-58** | **Unpaid venues are hidden from spectator search.** The on-hold treatment exists so an _artist_ understands why they cannot book. A spectator gains nothing from a venue they cannot visit; for them it is a dead result. `venues.list` (artist picker) and `discovery.suggestVenues` (spectator) therefore apply opposite rules to the same table — this is intentional, not an inconsistency to "fix".                                                                                   |
| **D-59** | **Collections are hidden**, following the events inside them.                                                                                                                                                                                                                                                                                                                                                                                                                              |
