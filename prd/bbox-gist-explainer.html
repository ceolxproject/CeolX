What is a Bounding Box Query?

When a user views the map the app sends the four corners of the visible viewport — SW and NE lat/lng — to the backend. PostgreSQL uses the GIST spatial index to instantly find only the events that fall within those bounds. No full-table scan. No distance calculations for every row.

Why the index matters

Without an index, PostgreSQL reads every row and checks if its lat/lng falls in the box — an O(n) full scan.

With a GIST index, the database navigates an R-tree, pruning entire branches that can't intersect the query box. Most rows are never touched.

At 500 events the difference is negligible. At 500,000 it's the difference between a 2ms query and a 2-second hang.

⚡ Redis caching layer

The query result is cached in Redis using the bounding box coords as the key (rounded to 4 decimal places).

Same drag area within 10s? Redis returns instantly — Postgres never runs.

This is the same "caching on map drag" benefit raised for Typesense — achieved with zero extra infrastructure.

What is a GIST Index?

GIST (Generalised Search Tree) is PostgreSQL's framework for indexing non-scalar data — including spatial coordinates. For lat/lng it builds an R-tree: a hierarchy of nested bounding boxes that covers all your data. Each node stores the minimum bounding rectangle (MBR) of its children. A query prunes any node whose MBR doesn't overlap the search box.

Creating the index

-- One-time migration — runs in seconds even on large tables
CREATE INDEX idx_events_spatial
  ON events
  USING GIST (
    point(lng, lat)
  );

Key point for map drag

A B-tree on lat can range-scan rows by latitude — but it has no knowledge of longitude. You'd need a second B-tree on lng, and Postgres would still intersect two large result sets. The GIST R-tree tests both dimensions simultaneously in a single traversal — this is why it's the right index type for map queries.

① Debounce (400ms)

React Native Maps fires continuous pan events. The app waits 400ms of inactivity before making an API call — preventing dozens of requests during a single drag. The user perceives this as instant because pins from the previous position remain visible during the drag.

② Payload — just 4 numbers

{ swLat, swLng, neLat, neLng } — the SW and NE corners of the visible viewport. Nothing else. No device location in this request, no user ID. The server derives everything it needs from these four values.

③ Redis key strategy

Coords are rounded to 4 decimal places (~11m precision at Irish latitude) before forming the cache key. This ensures small sub-pixel map jitter doesn't create unnecessary cache misses. TTL: 10 seconds.

Total P95: < 50ms

Debounce: 400ms wait (deliberate UX). API routing: ~1ms. Redis: ~1ms. Postgres GIST: ~3–8ms. Network (Ireland): ~20–30ms. Well within the 100ms threshold where users perceive interactions as instant.

Redis key structure

// Round to 4 decimal places (~11m precision) — nearby drags share the same key
const r4 = (n) => Math.round(n * 10000) / 10000;
const key = `bbox:${r4(swLat)}:${r4(swLng)}:${r4(neLat)}:${r4(neLng)}`;

// Example: "bbox:52.6341:-8.6240:53.1421:-7.9103"

const cached = await redis.get(key);
if (cached) return JSON.parse(cached); // ← Postgres never runs

const result = await db.getBoundingBoxEvents({ swLat, swLng, neLat, neLng });
await redis.setex(key, 10, JSON.stringify(result));
return result;

Recommendation: PostgreSQL + GIST + Redis

Every V1 requirement is handled by the current stack.

Typesense's caching advantage — the primary argument raised — is identically covered by Redis, which is already in the architecture. Adding Typesense in V1 means: 2–3 days build, a sync pipeline to maintain, $25–50/month extra infra, and a third service that can fail independently.

Future upgrade path

Typesense becomes the right choice when:

• Users search artist names / event titles with typo tolerance
• Feed needs dynamic facets with result counts
• Relevance ranking matters (boosting popular events)
• Scale grows beyond ~10,000 events in DB

The GIST index stays regardless — geo queries always live in Postgres.
